# LESR 产品范围与首批验证方案

## 1. 产品定位

Local Engineering Specification Runtime（LESR）不是一个单纯的 MCP
Server，也不以复制完整 ALM 平台为目标。

LESR 的产品能力分为三层：

1. **规范转换层**
   - 接收用户合法持有的 PDF、Word、Excel、Markdown 或结构化数据；
   - 识别条款、规则、流程、工程对象、关系和证据要求；
   - 生成待复核的 Profile、Artifact、Relation、Rule 等结构化对象；
   - 保留来源文件、版本、章节、页码和转换依据；
   - 经人工确认后发布为正式规范对象。
2. **规范运行时**
   - 使用 Git 管理的 YAML/Markdown 作为可审阅事实源；
   - 提供精确查询、全文检索、关系追踪和任务上下文组装；
   - 执行 Schema、Workflow、Relation Policy 和扩展规则校验；
   - 管理 Finding、Evidence、Change Request、Deviation 和 Baseline；
   - 保留版本历史与审计记录。
3. **MCP 接口层**
   - 将查询、上下文、校验、变更和基线能力提供给 Codex、Claude、
     Cursor 等 AI Host；
   - MCP 是 AI 调用 LESR 的标准接口，不是 LESR 的全部业务能力；
   - 敏感写操作必须由可信的人机交互流程确认，不能只依赖模型传入的
     用户名字符串。

## 2. 目标用户

- 需要让 AI 遵循企业工程规范的软件团队；
- 管理需求、设计、测试和变更追踪的小型工程团队；
- 准备 ASPICE 过程审计和客观证据的团队；
- 管理 C 语言编码规则、静态分析发现和偏离记录的团队；
- 希望以 Git 友好方式维护自定义工程规范的个人或组织。

## 3. MVP 输入与输出

### 3.1 支持的输入

首版优先支持：

- 具有可提取文本的 PDF；
- Markdown；
- 用户手工编写的 YAML Profile 和 Artifact；
- 静态分析工具导出的结构化结果，具体格式由适配器定义。

扫描 PDF、复杂 Word/Excel、OCR、表格结构恢复和任意自然语言文档的
全自动转换不作为首个纵向验证的硬目标。

### 3.2 规范转换输出

每个转换结果至少应包含：

- 稳定 ID；
- 对象类型；
- 标题和规范陈述；
- 约束强度或分类；
- 适用范围；
- 与其他对象的关系；
- 校验方式；
- 来源文件标识及版本；
- 来源章节和页码；
- 转换状态：`candidate`、`reviewed`、`approved` 或 `rejected`；
- 转换置信信息和人工修订记录。

未经人工复核的转换结果不得直接进入正式 Profile 或正式基线。

## 4. 首批纵向验证

### 4.1 场景 A：ASPICE SWE.1 软件需求分析

### 范围

首批只验证 SWE.1，不声明覆盖完整 Automotive SPICE。

需要表达：

- SWE.1 过程目的；
- 过程结果；
- BP1 至 BP6；
- 软件需求及其属性；
- 系统需求和系统架构来源；
- 软件架构关联；
- 分析结果；
- 一致性和双向可追溯性证据；
- 沟通及同意证据；
- Finding 和整改状态。

### 核心查询

- 某软件需求来源于哪些系统需求？
- 某软件需求与哪个系统架构和软件架构保持一致？
- 哪些 Approved 软件需求缺少上游来源、分析证据或验证关联？
- 修改某需求会影响哪些设计、测试、证据和基线？
- 为什么某项内容被选入当前 AI 任务上下文？

### 验收标准

- 每个转换对象均能定位到来源章节和页码；
- 人工黄金样本中的对象不得遗漏；
- 不得生成原文中不存在的规范性要求；
- 缺少必需关系时产生可解释 Finding；
- 需求变更生成新版本并保留旧版本；
- 正式对象变更需要人工确认并产生审计记录。

### 4.2 场景 B：少量 MISRA-like C 规则

### 范围

首批选择 5 至 10 条经许可可用于验证的规则 ID 或项目自有等价规则。
仓库不存储或分发受版权保护的完整 MISRA 正文。

需要表达：

- Rule 或 Directive；
- Mandatory、Required 或 Advisory；
- Decidable 或 Undecidable；
- Single Translation Unit 或 System 分析范围；
- 适用的 C 标准版本；
- 外部工具规则键；
- Finding、代码位置和工具证据；
- Deviation 的理由、风险、批准人、状态和有效范围。

### 核心查询

- 当前文件适用哪些编码规则？
- 某静态分析结果对应哪条规则和哪个代码位置？
- 哪些 Finding 尚未确认、修复或获得偏离批准？
- 某项偏离适用于哪些文件、版本和基线？

### 验收标准

- 能导入至少一种结构化静态分析结果；
- 能将结果稳定映射为 Finding 和 Evidence；
- Mandatory 规则不得通过偏离静默忽略；
- Required 规则的不符合项需要正式偏离流程；
- AI 不能自行批准偏离；
- 所有判断保留规则 ID、工具和代码版本来源。

## 5. 暂不纳入首版

- 完整复制或分发 ASPICE、MISRA 等商业或受版权保护标准；
- 自动宣称通过正式 ASPICE 评估或 MISRA 合规认证；
- 替代专业静态分析器；
- 完整 ALM、多人实时编辑和复杂组织权限；
- 无人工复核地把 AI 提取结果发布为正式规范；
- 无人工确认地修改 Approved 或 Baselined 对象；
- Web UI、图数据库和大规模向量数据库。

## 6. 可信度原则

LESR 输出应遵循：

- **可追溯**：每个结论都能返回来源；
- **可复现**：相同版本输入和配置得到稳定结果；
- **可解释**：说明选择、排除和校验原因；
- **可审阅**：结构化数据适合人类和 Git Diff；
- **可纠正**：人工修改不会被后续自动转换静默覆盖；
- **可审计**：变更、审批、版本和工具执行均有记录；
- **保守写入**：AI 默认提出建议，不替代正式审批；
- **版权安全**：只处理用户有权使用的内容，不默认再分发标准正文。

## 7. 协作与交付约定

- `main` 保持可运行，不直接用于日常开发；
- 每个 Issue 对应一个短生命周期分支；
- 分支命名使用 `feature/`、`fix/`、`docs/` 或 `test/`；
- 通过 Pull Request 合并；
- 合并前至少由另一位协作者审查；
- 合并前运行 ruff、pytest 和相关端到端验证；
- Pull Request 应说明目标、边界、验证方法和已知风险；
- 大型标准原文、许可证文件、密钥和本地运行数据库不得意外提交。

## 8. 待双方确认的问题

- 首版原始输入是否只支持文本型 PDF 和 Markdown？
- 规范转换是 AI 辅助人工确认，还是期望全自动发布？
- 来源页码和章节是否为所有正式对象的必填字段？
- ASPICE 首批是否确认只做 SWE.1？
- MISRA-like 首批使用哪些合法规则或项目自有替代规则？
- 首个静态分析结果适配器选择哪种工具和格式？
- 谁具有审批正式规范、Change Request 和 Deviation 的权限？
- 是否需要与现有 Git、CI、Issue 或 ALM 工具集成？
- 项目如何保存和验证标准的许可证及版本信息？
