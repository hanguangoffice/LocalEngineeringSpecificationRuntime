# 05A 规范模态、执行后果与冲突模型

**决策成熟度：FOUNDATIONAL；具体 Profile 映射 PROVISIONAL**

## 1. 问题

传统工具经常用一个 `severity` 字段同时表达：

- 规则是否强制；
- 违反后是否阻断；
- 工程风险有多大；
- 是否允许偏离；
- 工作项优先级。

这些概念彼此不同。将它们合并会使不同规范体系无法准确适配，也会让 LESR 自行猜测“严格程度”。

---

## 2. Normative Facet 的五个正交维度

```text
Modality
Applicability
Evaluation
Enforcement
Deviation Policy
```

Criticality 和 Priority 作为辅助信息，不能替代上述维度。

---

## 3. Core Normative Modality

### OBLIGATION

要求某个状态成立或某个行为发生。

例：

```text
Approved 软件需求必须至少有一个验证关系。
```

### PROHIBITION

禁止某个状态或行为。

例：

```text
Baselined 对象不得被原地覆盖。
```

### PERMISSION

明确允许某个原本受限制或需要确认的行为。

Permission 不是自动覆盖 Prohibition 的万能开关。它必须具有明确授权来源、作用域和优先关系。

### RECOMMENDATION

建议执行，违反不构成 Obligation Violation，除非用户规范另行定义执行后果。

### DISCOURAGEMENT

建议避免，但不等同于 Prohibition。

### INFORMATIONAL

只提供事实、解释或背景，不产生规范义务。

---

## 4. 标准术语映射

不同标准的标签可以映射到核心模态，但映射由 Profile 明确声明。

示例：

```text
某 Profile 的 “Mandatory”
→ OBLIGATION 或 PROHIBITION
+ deviation forbidden
+ baseline gate block

某 Profile 的 “Required”
→ OBLIGATION
+ deviation conditional
+ approval gate block

某 Profile 的 “Advisory”
→ RECOMMENDATION
+ review warning
```

LESR 不内置对具体商业标准等级的唯一解释。

---

## 5. Normative Target

规则必须尽量结构化说明它约束什么。建议的目标类别：

### STATE_CONSTRAINT

要求对象字段、状态或配置满足条件。

### OPERATION_POLICY

允许、禁止或要求某个操作。

### RELATION_REQUIREMENT

要求或禁止某类 Relation。

### CONTENT_REQUIREMENT

约束内容结构、质量或表达。

### PROCESS_REQUIREMENT

要求执行某个流程、评审或活动。

### EVIDENCE_REQUIREMENT

要求提供某类 Evidence。

### EXTERNAL_RULE

由外部工具或标准规则求值。

Profile 可以定义更具体的子类型，但必须映射到一个核心类别。

---

## 6. Applicability

Normative Rule 只有在 Applicability 成立时才参与求值。

输入可包括：

- Kind；
- Facet；
- Module；
- Path；
- Symbol；
- Language；
- Variant；
- Platform；
- Safety Level；
- Lifecycle Phase；
- Operation；
- State Transition；
- Configuration；
- 自定义条件。

Applicability 无法确定时，结果是 `INDETERMINATE`，不能当作不适用。

---

## 7. Evaluation Outcome

核心结果：

```text
SATISFIED
VIOLATED
NOT_APPLICABLE
INDETERMINATE
DEVIATED
NOT_EVALUATED
EVALUATION_ERROR
```

### DEVIATED

表示规则本身原本适用且未满足，但存在有效、覆盖当前 Scope 的批准 Deviation。

DEVIATED 不是 SATISFIED。审计和合规报告必须保留二者区别。

---

## 8. Enforcement

Enforcement 描述某个 Evaluation Outcome 对某项操作或状态转换产生什么后果。

候选 Effect：

```text
ALLOW
ALLOW_WITH_OBSERVATION
REQUIRE_REVIEW
REQUIRE_APPROVAL
BLOCK_OPERATION
ESCALATE
```

示例：

```yaml
on_violation:
  draft_edit: ALLOW_WITH_OBSERVATION
  submit_review: REQUIRE_REVIEW
  transition_to_approved: BLOCK_OPERATION
  create_baseline: BLOCK_OPERATION

on_indeterminate:
  draft_edit: ALLOW_WITH_OBSERVATION
  apply_change: REQUIRE_APPROVAL
  create_baseline: BLOCK_OPERATION
```

因此同一规则可以允许 Draft 探索，但阻止正式批准。

---

## 9. Criticality 与 Priority

### Criticality

表示违反后的工程影响，例如安全、功能、法规或交付风险。用于风险分析和排序。

### Priority

表示处理顺序。

它们不直接决定 Normative Modality，也不自动决定 Enforcement。

例如高 Criticality 的 Recommendation 仍然是 Recommendation，除非用户规范将其设为 Obligation。

---

## 10. Deviation Policy

至少表达：

```text
allowed: forbidden | allowed | conditional
required_approvals
required_evidence
maximum_scope
maximum_duration
compensating_controls
revalidation_triggers
```

Deviation 必须指向准确 Rule Revision，并绑定 Scope。

---

## 11. 冲突类型

### Direct Deontic Conflict

同一 Scope 和条件下：

- OBLIGATION 与 PROHIBITION 针对同一行为；
- PERMISSION 与 PROHIBITION 同时有效，但没有明确例外关系。

### Constraint Conflict

两个数值、枚举或关系约束没有共同可满足解。

### Enforcement Conflict

同一 Outcome 和 Operation 被要求同时 ALLOW 与 BLOCK。

### Deviation Conflict

一个 Profile 禁止偏离，另一个普通项目规则试图允许。

### Applicability Conflict

规则作用域计算互相矛盾或无法确定。

---

## 12. 冲突解析

解析顺序：

1. 确定准确 Rule Revision；
2. 计算 Applicability；
3. 应用显式 Exception、Authorization 和有效 Deviation；
4. 应用 Profile 定义的 Authority/Precedence；
5. 检查更具体规则是否被明确声明为 Refinement；
6. 计算约束交集；
7. 无法解析时返回 `NORMATIVE_CONFLICT`。

不能使用：

```text
后加载覆盖前加载
数值 severity 更高者获胜
项目规则天然高于安全规则
更具体规则永远获胜
```

除非用户规范明确声明。

---

## 13. Permission 的边界

Permission 只有满足以下条件之一时，才能改变 Prohibition 的效果：

- 被 Prohibition 的 Profile 明确声明为可授权例外；
- Permission 由被认可的 Authorization Object 产生；
- 有明确的 `exception_to` 或等价关系；
- Authority/Precedence 规则确定 Permission 优先。

否则 Permission 与 Prohibition 构成冲突。

---

## 14. 未解决冲突的行为

未解决冲突使相关 Effective Model 部分为 `INDETERMINATE`。

默认核心安全行为：

- 查询和 Draft 可以继续，但必须显示冲突；
- AI 不得自行选择；
- Apply、Approve、Deviation Approval 和 Baseline 等高风险操作暂停；
- 用户通过修改规范、增加明确裁决或批准 Deviation 解决。

这属于工具完整性，不是 LESR 自己选择更严格的工程规则。

---

## 15. AI 质量检查

AI 可以判断：

- 规则可能歧义；
- 两条自然语言规范可能冲突；
- Applicability 可能缺失。

这些结果为 Advisory Observation。正式冲突门禁必须基于结构规则、明确 Relation 或人工裁决。
