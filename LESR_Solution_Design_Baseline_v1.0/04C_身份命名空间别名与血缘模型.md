# 04C 身份、命名空间、别名与血缘模型

**决策成熟度：FOUNDATIONAL；UID 与 URI 格式 PROVISIONAL**

## 1. 设计目标

身份模型必须同时满足：

- 人可读；
- AI 可精确寻址；
- Git 中可稳定恢复；
- 跨版本稳定；
- 导入导出时不冲突；
- 对象改名、移动、拆分和合并后关系仍可追溯；
- 不把文件路径、模块、状态或当前类型编码成不可变身份。

---

## 2. 五类标识

### 2.1 Internal UID

系统永久身份：

```text
entity_uid
```

性质：

- 创建后永不改变；
- 永不复用；
- 不包含业务语义；
- 不依赖文件路径；
- 用于内部关系、合并、导入和数据库主键；
- 用户通常无需手工输入。

具体采用 UUID、ULID、UUIDv7 或其他格式属于实现候选。

### 2.2 Human Key

工程沟通编号：

```text
REQ-SW-001
RULE-C-014
TEST-COM-021
```

性质：

- 人可读；
- 在命名空间内唯一；
- 可由 Profile 定义格式；
- Draft 阶段可修改；
- Approved 或对外发布后通过 Alias 迁移；
- 可由用户规范冻结。

### 2.3 Revision UID

某个不可变正式版本的唯一身份：

```text
revision_uid
revision_number
```

Revision Number 供人阅读；Revision UID 用于准确引用和跨仓库操作。

### 2.4 Record UID

Immutable Record 的身份，例如：

- Test Execution；
- Observation；
- Approval Attestation；
- Audit Event；
- Provenance Activity。

Record 默认不使用可变 Revision，而通过新 Record 纠正。

### 2.5 Fragment Address

Fragment 只有局部地址：

```text
lesr://<logical-object>@<revision>#<fragment-path>
```

Fragment Address 只在准确父 Revision 内有效。

---

## 3. Logical Object

Logical Object 是跨 Revision 持续存在的语义主体。

```text
Logical Object
├─ Revision 1
├─ Revision 2
├─ Revision 3
└─ 当前或历史 Workspace Candidate
```

Logical Object 本身保存：

- Internal UID；
- Human Key；
- Alias；
- Namespace；
- Kind 历史；
- Disposition；
- Lineage；
- 可用 Revision 索引。

内容、字段和大部分 Facet 值属于 Revision。

---

## 4. Namespace

Namespace 用于解决多个项目、Profile、导入源和对象类别之间的 Human Key 冲突。

候选组成：

```text
authority / repository / project / domain
```

例如：

```text
company/project-a/communication
external/customer-x/requirements
profile/misra-like
```

Namespace 不等于文件目录。移动文件不改变 Namespace；改变 Namespace 是显式语义操作。

具体 URI 语法仍为 `PROVISIONAL`。

---

## 5. Alias

Alias 用于保持历史编号和外部引用可解析。

Alias 至少包含：

```yaml
alias: REQ-SW-001
alias_type: former_human_key
valid_from: ...
valid_to: ...
introduced_by: CHG-014
```

Alias 不得：

- 指向多个活动对象；
- 被重新分配给不相关对象；
- 静默覆盖当前 Human Key；
- 替代永久 UID。

---

## 6. Human Key 变更策略

### Draft

允许直接改名，但仍需唯一性检查和 Workspace 审计。

### Approved

通过 Change 修改 Human Key，并自动保留旧 Key 为 Alias。

### External Published

Profile 可规定 Human Key 永久冻结，只能通过新对象和 `supersedes` 关系替代。

该策略由用户规范决定，LESR 提供 Alias 和稳定 UID 机制。

---

## 7. 拆分、合并与血缘

### 拆分

原对象保留历史身份，新对象获得新 UID：

```text
OLD
├─ split_into NEW-A
├─ split_into NEW-B
└─ split_into NEW-C
```

原对象通常进入 `superseded`，不删除。

### 合并

多个对象合并为新对象：

```text
OLD-A ─┐
       ├─ consolidated_into NEW
OLD-B ─┘
```

### Fragment Promotion

Fragment 提升后：

```text
NEW extracted_from OLD@revision#fragment
```

### 移动

模块、Owner、文件路径或 Profile 变化不创建新身份；是否产生新 Revision 由语义字段变化决定。

---

## 8. 身份不变量

1. Internal UID 永不复用；
2. Revision UID 永不复用；
3. 正式 Revision 不可修改；
4. Fragment Address 必须固定父 Revision；
5. Human Key 在有效 Namespace 内唯一；
6. Alias 不得产生活动歧义；
7. 拆分和合并不得删除来源对象；
8. 导入对象必须保留 External ID 与来源；
9. 文件路径不能作为唯一身份；
10. Git Commit 不能作为对象身份。

---

## 9. 外部身份

External Reference 保存：

- system；
- namespace；
- external_id；
- external_revision；
- URI；
- imported_at；
- mapping_confidence；
- source_hash。

External ID 可以重复出现在不同系统或命名空间中。

---

## 10. 当前已接受结论

- Internal UID 与 Human Key 分离；
- Human Key 支持 Alias；
- Draft 可改名；
- Approved 后改名保留 Alias；
- 外部发布后可由 Profile 冻结；
- Logical Object 与 Revision 分离；
- Fragment 没有独立身份；
- 拆分、合并和提升通过 Lineage Relation 表达；
- 身份永不复用。

---

## 11. 尚未冻结

- UID 格式；
- Namespace URI；
- Human Key 默认生成器；
- 跨仓库 UID 冲突处理；
- Alias 的最长保留策略；
- External ID 往返规则。

## 12. Human Key 与 Revision

Human Key 作为工程语义元数据进入 Object Revision。Approved 对象改名会创建新 Revision，并建立旧 Human Key Alias；Internal UID 保持不变。

Logical Object 索引可显示当前有效 Human Key，但其历史必须从 Revision 和 Alias Record 恢复。
