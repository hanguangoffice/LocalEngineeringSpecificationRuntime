# 09A 关系角色、谓词与追踪语义

**决策成熟度：FOUNDATIONAL；Core Role 清单可由原型微调**

## 1. 三层关系模型

```text
Core Relation Role
    LESR 跨 Profile 理解的稳定语义族

Profile Relation Type
    具体领域谓词、端点、基数、绑定和追踪规则

Relation Assertion
    某两个端点之间的具体关系事实
```

Core Role 不是用户看到的唯一关系名。Profile 可以定义更精确的词汇，同时映射到核心角色。

---

## 2. Core Relation Role

### ORGANIZES

只用于集合、导航和发布组织，不表示语义分解或实现。

示例：Collection organizes Requirement。

### COMPOSES

表示结构上的整体与部分。

示例：Component contains Port。

默认不传播状态、适用性和批准。

### REFINES

源对象增加细节、约束或分解目标对象的语义。

示例：Software Requirement refines System Requirement。

### REALIZES

源对象实现、满足或具体化目标对象。

示例：Design realizes Requirement；Code Module realizes Design。

### VERIFIES

源对象定义或执行对目标对象的验证。

示例：Test Case verifies Requirement。

Test Execution 通常通过 Evidence Relation 支持验证结果，而不是直接取代 Test Case 的 VERIFIES。

### CONSTRAINS

源规则或定义限制目标对象的合法状态或行为。

### APPLIES_TO

显式声明 Profile、Rule、Deviation 或 Configuration 的作用范围。

### DEPENDS_ON

源对象依赖目标对象。

### IMPACTS

源变化、问题或对象影响目标。常用于影响分析，可能是推断关系。

### EVIDENCES

源 Evidence 或 Record 支持目标对象、Relation、Issue 或 Decision。

### GOVERNS

源 Workflow、Profile、Policy 或 Process Definition 治理目标对象。

### AUTHORIZES

源 Approval、Delegation 或 Deviation 授权某个操作、变化或例外。

### DERIVES_FROM

源内容、Revision、Record 或对象由目标来源产生。

### SUPERSEDES

较新的对象、Revision、Relation 或 Decision 取代较旧者。

### CONFLICTS_WITH

两个对象、规则或关系在当前 Scope 下存在冲突。通常是对称关系。

### REFERENCES

弱语义引用，不自动产生追踪、实现、验证或适用性效果。

## 3. Profile Relation Type

Profile Relation Type 至少定义：

```text
type_id
version
core_role
forward_label
inverse_label
source_kind/facet constraints
target_kind/facet constraints
allowed_binding_modes
default_binding_mode
formal_trace_credit
cardinality
symmetric
acyclic
path_query_semantics
evidence_policy
lifecycle
applicability
propagation_policy
inference_policy
```

---

## 4. 为什么不只使用 Core Role

`REALIZES` 过于宽泛。项目可能需要区分：

- architecture_allocates_requirement；
- detailed_design_implements_architecture；
- source_module_implements_design；
- calibration_realizes_parameter_requirement。

它们共享跨领域查询能力，但有不同端点、基数和工程含义。

---

## 5. Canonical Direction

Relation Type 必须声明唯一存储方向。推荐使用主动语义：

```text
child refines parent
design realizes requirement
test verifies requirement
rule constrains object
evidence evidences assertion
approval authorizes change
new supersedes old
derived derived_from source
```

反向查询使用 inverse label，不保存第二条重复边。

---

## 6. Relation Assertion 身份

Relation Assertion 具有自己的 Logical ID 和 Revision。

以下字段是身份承载字段：

- source endpoint；
- relation type；
- target endpoint；
- binding mode；
- applicability/scope。

改变任一身份承载字段时：

1. 创建新的 Relation Assertion；
2. 旧 Assertion 转为 retired 或 superseded；
3. 通过 Change Record 说明替换原因。

不能让同一个 Relation ID 从连接 A→B 变成 A→C。

---

## 7. 可修订字段

同一 Assertion 的 Revision 可以更新：

- rationale；
- supporting evidence；
- review status；
- lifecycle state；
- non-semantic annotation。

若这些变化实质改变关系含义，仍应创建新 Assertion。

---

## 8. Binding Mode

### Logical

端点是 Logical ID，由当前 Configuration 解析。

### Pinned

端点是准确 Revision。

### Fragment

端点是父 Revision + Fragment Address。

### External

端点是外部 URI/ID，可附 Commit、Hash、Version 或 Fingerprint。

Relation Type 必须限制允许的 Binding。

---

## 9. Formal Trace Credit

关系是否满足追踪要求不能仅靠 Core Role。

Profile Relation Type 必须声明：

```text
trace_credit:
  categories:
    - upstream_source
    - realization
    - verification
  accepted_assertion_kinds:
    - asserted
    - imported_verified
  accepted_states:
    - active
  accepted_bindings:
    - logical
    - pinned
```

默认：

- proposed 不计；
- inferred 不计；
- fragment 不计；
- retired 不计；
- weak reference 不计。

---

## 10. Inferred Relation

AI、规则或相似度可以生成 Inferred Relation Candidate。

它必须包含：

- inference method；
- input Revision；
- confidence；
- explanation；
- time；
- Agent/Tool。

Promotion 后创建新的 asserted Relation Assertion，并保留 `derived_from` 推断记录。不能原地把 inferred 状态改成正式事实。

---

## 11. Cardinality 与图约束

Relation Type 可以声明：

- min/max count；
- source/target state；
- acyclic；
- symmetric；
- self-loop；
- uniqueness；
- required evidence；
- path constraints。

默认不假设 transitive。即使可以沿 `refines` 链查询，也不自动生成直接 `refines` 断言。

---

## 12. Propagation

Relation 默认不传播任何属性。

若 Profile 声明：

```text
Applicability 沿某 Relation Type 向子对象派生
```

该结果应是可解释的 Effective Property，而不是复制字段。

Propagation Rule 必须：

- 指定属性；
- 指定方向；
- 指定冲突策略；
- 指定最大深度；
- 防止循环；
- 记录路径。

---

## 13. Relation 与 Baseline

Baseline 包含：

- Relation Assertion Revision；
- Logical Endpoint 的解析结果；
- Relation Type Revision；
- Effective Applicability；
- Trace Credit 计算所需 Profile。

因此同一逻辑关系在不同 Baseline 中可以解析到不同对象 Revision，但 Assertion 本身仍可保持稳定。

---

## 14. Relation 与 Evidence

正式关系可以要求 Evidence，例如：

- 安全需求到测试的验证关系需要评审记录；
- 偏离授权需要 Approval Attestation；
- 外部导入关系需要来源文件指纹。

Evidence 通过 EVIDENCES Role 连接 Relation Assertion，而不是仅作为自由文本字段。

---

## 15. 核心 Role 的扩展边界

Profile 可以新增 Relation Type，但必须映射到一个 Core Role。

若某领域确实无法映射，可以提出 namespaced Extension Role。Extension Role：

- 不能自动获得核心追踪语义；
- 必须定义查询和导出行为；
- 必须通过兼容性评审；
- 不得重定义已有 Core Role。
