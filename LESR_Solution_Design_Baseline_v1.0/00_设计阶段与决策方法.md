# 00 设计阶段与决策方法

**决策成熟度：FOUNDATIONAL**

## 1. 为什么现在不能直接冻结实现

LESR 同时涉及需求管理、规则执行、知识检索、AI 上下文、版本控制和工具互操作。过早确定“Python + SQLite + 一组 MCP 工具”容易产生三类问题：

1. 为某个实现方便牺牲长期语义；
2. 把 ASPICE、MISRA 等差异掩盖在不断膨胀的字段中；
3. 在尚未验证 AI 使用效果时，先投入大量基础设施。

因此当前阶段的产出应是**可验证的设计假设**，不是最终施工图。

## 2. 设计决策模板

每项关键决策应记录：

```yaml
decision_id: DD-XXX
question: 需要决定的问题
status: OPEN | PROVISIONAL | ACCEPTED | DEFERRED
context: 为什么需要决定
options:
  - option
  - advantages
  - disadvantages
constraints:
  - 不可违反的条件
current_leaning: 当前倾向
evidence_needed:
  - 需要哪些实验或数据
reversal_cost: 改变决定的代价
decision_deadline: 在哪个阶段前必须决定
```

## 3. 决策顺序

必须按以下顺序推进：

### 第一组：语义

- 规范对象的最小共同语义是什么；
- Requirement、Rule、Process Outcome 是否是不同基类；
- Document 与原子规范条目是什么关系；
- Relation 是否是一等实体；
- 版本、状态、适用范围和偏离如何表达。

### 第二组：行为

- Profile 如何组合；
- 规则如何求值；
- AI 上下文如何构建；
- 变更如何被提出、验证、批准和应用；
- 基线如何冻结。

### 第三组：接口

- 人和 AI 需要哪些能力；
- MCP 中哪些内容属于 Resource，哪些属于 Tool；
- 查询是否需要 DSL；
- 写操作的事务和并发语义是什么。

### 第四组：实现

- 文件格式；
- 数据库；
- 规则引擎；
- 编程语言；
- SDK；
- UI；
- 部署方式。

跳过前两组直接讨论数据库，会使系统被存储结构反向塑形。

## 4. 评价维度

| 维度 | 核心问题 |
|---|---|
| 语义表达力 | 能否自然表示不同规范 |
| 可解释性 | 人能否看懂系统为何做出判断 |
| 可审计性 | 是否能还原谁在何时为何改变了什么 |
| AI 友好度 | AI 是否能稳定查询和调用 |
| 人工可维护性 | 用户是否能脱离专用 UI 编辑和审查 |
| 可迁移性 | 是否容易导入导出和更换实现 |
| 本地性 | 是否能完全离线运行 |
| 复杂度 | 个人项目是否承担得起 |
| 可逆性 | 早期选择错误时是否容易替换 |
| 性能 | 在目标规模下是否足够 |
| 安全性 | AI 和插件能否被约束 |

## 5. 方案验证原则

### 5.1 用真实任务验证

不以“能存 100 条需求”为验证标准。必须使用真实任务，例如：

- 修改一个 C 模块时，是否能准确找出所有适用规则；
- 修改系统需求时，是否能指出下游设计和测试；
- 新增偏离时，是否能识别批准条件；
- AI 是否能在不读取全库的情况下完成任务。

### 5.2 评价错误而非只评价成功

需要观察：

- 漏掉强制规范；
- 引入无关规范；
- 使用已废弃版本；
- 错误解析 Profile 优先级；
- 让 AI 绕过审批；
- 无法说明选择理由；
- 数据库与文件失配。

### 5.3 保留可替换边界

需要使以下部分可以独立替换：

- 存储；
- 检索；
- 规则执行；
- MCP SDK；
- 向量模型；
- UI；
- 外部工具适配器。

## 6. 当前阶段完成标准

方案设计阶段完成，不代表所有文档无未决项。其完成标准是：

1. 核心概念有清晰定义；
2. 主要备选方案被列出；
3. 暂定倾向有理由；
4. 高风险假设有实验；
5. 实现团队知道哪些内容不能自行猜测；
6. 能据此开展有限原型，而不会误以为要完成整个产品。

## 7. 方案基线决策记录规则

已接受的基础决策必须在 `决策记录/` 中单独保存。后续改变这些决定时，应创建新的决策记录并说明取代关系，不能只覆盖原文。
