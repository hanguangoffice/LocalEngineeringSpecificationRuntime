# 01 问题定义与使用场景

**决策成熟度：FOUNDATIONAL**

## 1. 根本问题

用户拥有 ASPICE-like、MISRA-like、架构、接口、测试及项目自定义规范。它们不能继续只作为文档片段供 AI 通过 grep、全文读取或普通 RAG 临时发现。

LESR 的根本目标是：

> 将用户编写的工程规范转化为具有稳定身份、明确关系、可执行约束、受控变更和可解释 AI 上下文的本地工程语义。

LESR 不负责替用户决定应该多严格。用户定义规范，LESR 忠实执行。

---

## 2. 已确定的环境约束

- Git 必须存在；
- 正式工程状态必须能从 Git 恢复；
- AI 可以在用户授权范围内连续处理 Draft；
- Approved、Baselined、Profile、Deviation Approval 等高风险对象不能被委托会话静默修改；
- Markdown 可以存在，但不作为主要领域编辑方式；
- 查询数据库、全文索引和向量索引均为可重建投影。

---

## 3. 主要角色

### 规范所有者

定义 Kind、Rule、Applicability、Workflow、Deviation Policy 和 Context Policy。

### 工程实施者

使用 LESR 查询有效规范、提出变更和审查影响。

### AI Agent

在被授予的能力和范围内查询、生成 Draft、修复 Draft、运行校验和提交评审。

### 评审者与批准者

审查正式变更、偏离、Profile 升级和 Baseline。

### 外部工具

产生 Observation、Evidence 和 External Reference，不直接修改权威语义状态。

---

## 4. 核心使用场景

### UC-01 代码修改前获取 Context Contract

系统必须区分：

- 强制 Read Set；
- 条件适用规则；
- 支持资料；
- 过期和禁止内容；
- 当前偏离；
- 缺失信息；
- 选择原因。

### UC-02 需求变更与影响分析

以准确 Revision 为基准打开 Change Workspace，形成候选 Revision、Relation 变更、影响路径、Finding、审批条件和最终 Git 变更。

### UC-03 新增规范 Profile

用户定义规范的概念、Kind、Facet 约束、规则、流程和上下文策略。LESR 不为该项目提供额外“严格度模式”。

### UC-04 导入静态分析或测试结果

工具输出进入系统后首先成为不可变 Observation 或 Evidence。是否形成需要跟踪的 Issue、Change 或 Deviation，由项目规范决定。

### UC-05 AI 连续处理低风险 Draft

用户一次授权：

```text
工作区：CHG-014
范围：communication 模块
允许：创建和更新 Draft、提出 Relation、运行校验
禁止：批准、建立基线、修改 Profile、修改 Approved/Baselined
```

AI 可以连续修改 Draft，直到：

- 超出范围；
- 需要高风险操作；
- 出现冲突；
- 基准 Revision 变化；
- 授权到期；
- 项目规则要求人工介入。

### UC-06 精确语义查询

AI 应能按对象、关系、版本、基线、Facet、Profile 和 Fragment 查询，不依赖文件行号和 Markdown 标题。

### UC-07 生成阅读文档

LESR 可以将语义对象和 View 渲染为 Markdown、HTML、PDF 或其他文档，但渲染结果不自动成为新的权威事实源。

---

## 5. 失败场景

- 强制规则因向量相似度低而漏召回；
- Draft 授权被误当成正式批准；
- 外部扫描结果被直接编辑；
- Markdown 文件标题被误当成对象身份；
- 父对象属性未经规则说明自动继承到子对象；
- Relation 跟随错误版本；
- 项目规则冲突时系统自行选择“更合理”的严格程度；
- 已过期偏离继续生效；
- 查询数据库损坏后无法从 Git 恢复。

---

## 6. 成功标准

LESR 成功的关键不是保存更多文档，而是：

- AI 能找到正确的工程对象；
- AI 知道对象为什么适用；
- 用户能决定规则强度；
- Draft 自动化不越权；
- 正式变化可审查、可恢复；
- 标准差异通过 Profile 表达；
- Git 保存完整、确定性的语义状态。
