# 02 设计原则与系统边界

**决策成熟度：FOUNDATIONAL**

## DP-01 用户规范是工程裁决来源

LESR 不提供全局“宽松、普通、严格”模式。规则的 Normative Modality、Enforcement、Deviation 和 Approval 由用户编写的规范决定。

规范没有明确裁决时，LESR 返回 `INDETERMINATE`，不能自行补充工程政策。

## DP-02 Git 是必需基础设施

所有正式对象、关系、Profile、Tailoring、Deviation、Change 结果和 Baseline 必须能够从 Git 中恢复。运行时数据库不是唯一事实源。

## DP-03 领域编辑优先于原始文件编辑

用户和 AI 通过本地 UI、MCP、CLI 或领域 API 修改语义对象。Git 中的结构化表示必须可审计和可恢复，但不要求用户日常直接编辑。

## DP-04 Markdown 是视图，不是主要语义内核

Markdown 适合阅读、报告、发布、导入和长篇说明。对象身份、关系、状态、版本、Profile 和事务不能依赖 Markdown 结构。

## DP-05 原子性由治理责任决定

原子对象的判断依据是能否独立版本、批准、追踪、验证、适用或偏离，而不是句子、段落和文件。

## DP-06 封闭核心类别，开放 Kind

内核只维护少量稳定资源类别。ASPICE-like、MISRA-like 和自定义领域类型通过 Facet 与 Profile Kind 组合，不通过修改内核继承树实现。

## DP-07 Relation 是一等断言

关系拥有身份、Revision、来源、绑定方式、状态和可选 Evidence。反向显示不需要复制第二条关系。

## DP-08 事实、记录和推断分离

- Governed Object 表示可治理语义；
- Immutable Record 表示已发生观察或活动；
- Inferred Relation 表示推断；
- Issue 表示对 Observation 的治理响应。

## DP-09 Draft 自动化与正式批准分离

Scoped Delegation 只允许在授权范围内连续处理 Draft，不表示用户预先批准最终正式变更。

## DP-10 普通层级不产生隐式继承

`groups`、`contains`、`decomposes_into` 不默认传播状态、优先级、适用性和安全等级。传播只能由 Profile 明确声明，并且必须可解释。

## DP-11 查询投影可重建

结构索引、全文、图缓存和向量均是派生数据。投影状态不完整时，系统必须显式降级，不能静默给出完整性结论。

## DP-12 高风险结果由确定性策略门禁

AI 可以提出建议、生成摘要和发现候选关系；批准、基线、不可偏离规则和权限门禁必须由确定性逻辑执行。

---

## 系统负责

- 身份与 Revision；
- Kind 与 Facet；
- Relation Assertion；
- Profile 编译；
- Applicability 和 Rule 求值；
- Context Contract；
- Change Workspace；
- Scoped Delegation；
- Validation、Observation、Issue；
- Deviation；
- Baseline；
- Provenance；
- Git 状态映射；
- 查询和适配器边界。

## 系统不负责

- 替用户制定标准；
- 分发商业标准全文；
- 对工程风险作最终责任判断；
- 将模型建议自动视为批准；
- 用普通全文搜索替代正式关系；
- 把外部工具结论当成不可质疑事实；
- 通过 UI 选项临时改变规范强度。
